## 1. P1 范围

做：
1. 通用 JSON-RPC over NDJSON stdio 客户端。
2. 通用 ACP 进程封装（spawn、initialize、stderr 脱敏、超时、进程组终止）。
3. 每账号一个 agy ACP 进程的进程池（懒启动、空闲回收、退出清理）。
4. agy ACP 会话适配：`RunSpec` → ACP 调用；`session/update` → 现有 `AgentEvent`；对外仍返回 `RunHandle`。
5. 权限请求**由主进程按 `autoApprove` 自动回答**（P1 不弹 UI，见 3.6）。
6. 每轮结束后读会话 sqlite 检测“伪装成 end_turn 的上游错误”（设计 11.1）。
7. 账号级开关 `agyTransport: 'print' | 'acp'`，默认 `'print'`；Gemini 账号设置弹窗里加一个开关。
8. ACP 启动失败自动回退到 `-p`。
9. 单元测试。

## 3. 详细要求

### 3.1 `jsonrpc.ts`
- 构造参数：可写流（stdin）、可读流（stdout）、`onLog(line)`。
- 按 `\n` 切行，逐行 `JSON.parse`；非 JSON 行交给 `onLog`，不要抛。处理半行缓冲。
- `request(method, params, timeoutMs)`：自增 id，返回 Promise；超时 reject 并删除挂起项。
- `notify(method, params)`。
- 收到带 `id` 且有 `method` 的消息 = **agent 发来的请求**：调用注册的 handler（`onRequest(method, params) => Promise<result>`），把结果或 `{code:-32601}` 错误回写。没有 handler 的方法回 `-32601 Method not found`。
- 收到无 `id` 有 `method` 的消息 = 通知，交给 `onNotification`。
- 收到带 `id` 无 `method` = 响应，配对挂起请求；`error` 字段 → reject 一个带 `code`/`message`/`data` 的 Error。
- `close(reason)`：让所有挂起请求以 reason reject，之后的 request 立即 reject。

### 3.2 `stderr.ts`
- 单条 chunk 超过 32KB 只保留最后 32KB；整体尾部只保留最后 4KB（用于报错信息）。
- `sanitize(text, home)`：去掉 `\0`；把 `home`（隔离 HOME）和真实 HOME 替换成 `~`；替换：
  - `https?://accounts.google.com\S*` → `[sign-in-url]`
  - `Bearer <token>` → `Bearer [redacted]`
  - `Authorization: Basic \S+` → `Authorization: Basic [redacted]`
  - `x-api-key: \S+` → `x-api-key: [redacted]`
  - `sk-…`（8 位以上）、`ghp_…`、`xox?-…`、`ya29.…`（Google access token）、`AIza…`（Google API key）→ `[redacted]`
- **所有 stderr 进 `onLog` 之前都要先脱敏**；JSON-RPC 的原始 stdout 行进 `onLog` 前也要用同一个函数脱敏。

### 3.3 `acpProcess.ts`
- `startAcpProcess({ bin, args, env, cwd, onLog, onRequest, onNotification })`：
  - `spawn(bin, args, { env, cwd, detached: true, stdio: ['pipe','pipe','pipe'] })`（detached = 独立进程组）。
  - `initialize`，参数：`{ protocolVersion: 1, clientCapabilities: { fs: { readTextFile: false, writeTextFile: false }, terminal: false }, clientInfo: { name: 'agentswitch', version: <app version> } }`。**fs 两项必须 false**（设计 11.7）。
  - initialize / 之后的 `session/new`、`session/resume` 都设 **90s** 超时。
  - 进程退出时：等 stderr 读完（最多 250ms），再用脱敏后的 stderr 尾部组装错误信息，`close()` JSON-RPC。
  - 记录 `agentInfo.version` 与 `agentCapabilities` 到 `onLog`。
- `terminate()`：对**进程组**发 SIGTERM（`process.kill(-pid, 'SIGTERM')`），1s 后进程组还在就 SIGKILL；幂等。
- 对外暴露：`rpc`、`initializeResult`、`exited: Promise<string>`、`terminate()`、`alive`。

### 3.4 `pool.ts`
- key = `profileId`（设计已改为会话保持 `default` 模式，不需要按权限分进程）。
- `acquire(profileId)`：没有或已退出就新建；正在启动时并发调用要复用同一个启动 Promise。
- 进程 env 用 `buildSpawnSpec(id, 'run').env`（自动带隔离 HOME、钥匙串、清理后的变量）；bin 用 `kindBinaryPath('gemini')`；args `['acp']`；cwd 用 `realHome`。
- 空闲回收：最后一个活动会话结束后 10 分钟没有新请求就 `terminate()`；**如果还有 `in_progress` 的 execute 类工具**（设计 11.5）就推迟回收（每 10 分钟再查一次，最多推迟 1 小时）。
- `retire(profileId)`、`shutdownAll()`（应用退出时调用，同步发 SIGTERM 即可）。
- 一个进程会服务多个会话：通知按 `params.sessionId` 分发到对应会话的监听者；没有监听者的会话事件只写 `onLog`（设计 11.5 的“本轮结束后的迟到事件”）。
- 进程池负责处理 agent → client 请求 `session/request_permission`，按 `sessionId` 交给对应会话处理；找不到会话就回 `{ outcome: { outcome: 'cancelled' } }`。

### 3.5 `agySession.ts` —— 一轮的流程
对外 `runAgyAcp(spec: RunSpec, emit, onLog): RunHandle`，返回值语义与现有 `runAgent` 完全一致（`RunResult` 各字段含义不变）。

1. `pool.acquire(cfg.id)`。
2. 会话：
   - `spec.resume` 有值：本进程里这个 sessionId 已经激活过就直接用；否则 `session/resume { sessionId, cwd: spec.cwd, mcpServers: [], additionalDirectories: [] }`（**额外目录字段每次都带**，设计 11.7）。resume 失败 → `emit notice`（文案走 i18n）后 `session/new`。
   - 没有 resume：`session/new { cwd, mcpServers: [], additionalDirectories: [] }`。
   - **绝不调用 `session/load`**（不存在的 ID 会静默新建，设计第 2 节）。
   - system prompt：`initializeResult.agentCapabilities._meta.antigravity.systemPrompt.append === true` 时放进 `session/new` / `session/resume` 的 `_meta: { antigravity: { systemPrompt: { append: spec.system } } }`；否则按现有 `full(s)` 的方式拼到 prompt 前面。注意：同一会话 resume 时 system 要再传一次。
   - 拿到 sessionId 立刻 `emit({ t: 'session', id, model })`。
3. 模型：`splitSpec(spec.model)`（见 `@shared/modelSpec`）得到 `model` / `effort`。从会话返回的 `configOptions` 里找 `id === 'model'` 和 `category === 'thought_level'` 的选项：
   - 模型值在 `model` 选项里能找到（或 `spec.model` 以某个选项值加 `-` 开头，旧格式，设计 11.8）→ 用 `session/set_config_option { sessionId, configId, value }` 设置；**每次 resume 后都要按 AgentSwitch 的选择重新设置，不能沿用 resume 返回的 currentValue**。
   - effort 有值且 `thought_level` 选项里有这个值 → 同样设置。
   - 先写一个探测脚本确认 1.5.14 上 `session/set_config_option` 的确切方法名 / 参数（脚本放 `/tmp`，不要进仓库）；如果方法名不同，按实测改，并在交付说明里写明。
   - 设置失败不要让整轮失败：`emit notice` 后继续用当前模型。
   - `set_config_option` 返回之前收到了 `config_option_update` 通知的，以通知为准。
4. 模式：会话一直保持 agy 的 `default` 模式（不调 set_mode，也不传 `--dangerously-skip-permissions`）。
5. 图片：`spec.images` 里每张 ≤ 5MB 且扩展名是 png/jpg/jpeg/gif/webp 的，读成 base64，作为 `{ type: 'image', mimeType, data }` 放进 prompt 数组；其余的按现有方式把路径写进文本。只在 `promptCapabilities.image === true` 时发图片块。
6. 同一 sessionId 必须串行：上一个 `session/prompt` 还没返回时，后来的同会话 prompt 要排队等待（设计 11.9）。
7. 发 `session/prompt { sessionId, prompt: [...] }`，**超时不设**（一轮可能很长），由 stop / 进程退出结束。
8. 事件映射（设计第 5 节）：
   - `agent_message_chunk`（content.type === 'text'）→ `{ t: 'text', delta }`；与现有 agy adapter 一样，不同消息段之间补 `\n\n`。
   - `agent_thought_chunk` → `{ t: 'thinking', delta }`。
   - `tool_call` / `tool_call_update` → 构造一个对象喂给现有 `agyTool()` 复用分类逻辑：`{ step_index: toolCallId, tool_name: name ?? title, state: status 映射（pending/in_progress→ACTIVE，completed→DONE，failed→ERROR）, tool_info: { name, parameters: rawInput ?? args, output: <从 content / rawOutput 里取文本> } }`。`id` 必须稳定为 `agy:<toolCallId>`，同一个工具的多次 update 要更新同一张卡片。`kind === 'execute'` 时一定归为 run 类型。
   - `usage_update { used, size }` → 记录 `used` 作为上下文。
   - `session_info_update`、`available_commands_update` → 忽略。
   - 其他 → `other(...)` 事件（沿用 200 条上限，那个上限在 `runAgent` 的 `wrapped` 里，ACP 分支也要走同一个包装）。
   - `session/prompt` 结果 `usage` → `{ t: 'usage', usage: { input: inputTokens, output: outputTokens, cacheRead: cachedReadTokens || undefined, reasoning: thoughtTokens, context: used || undefined } }`。
9. 结果：
   - `stopReason === 'end_turn'` 先当成功，再做 3.7 的错误检测。
   - `cancelled` → `stopped: true`。
   - `max_tokens` / `max_turn_requests` / `refusal` / 其他 → `ok: false`，error 写原因。
   - JSON-RPC 错误或进程退出 → `ok: false`；错误文本匹配现有 `RATE_LIMIT_RE` 时 emit `{ t: 'rate_limited' }` 并 `rateLimited: true`。
10. 本轮结束后，把仍处于 `in_progress` 的工具卡片发一次 `status: 'done'` 并在 detail 里注明“后台继续运行”（文案 i18n），避免界面一直转圈。
11. `onLog`：沿用现有格式先打一行 `── <账号名> · <模型> · cwd <cwd>`，然后 `$ agy acp (session <id>)`；后续收发的 JSON-RPC 行（脱敏后）都进 `onLog`，方便调试抽屉排查。

### 3.6 权限请求（P1 自动回答）
`session/request_permission { sessionId, toolCall, options }`：
- 按 `option.kind` 找选项，不要写死 optionId。
- `toolCall.toolCallId` 以 `interaction_` 开头 = agy 在问用户问题（设计 11.4）。P1 没有 UI：回 `{ outcome: { outcome: 'cancelled' } }`，并 `emit notice`（“Gemini 提了一个需要你回答的问题，ACP 模式暂不支持界面作答，已跳过”之类，i18n）。
- 其他请求按账号 `autoApprove`：
  - `full` → 选 `allow_once`。
  - `edits` → `toolCall.kind` 是 `edit` / `delete` / `move` / `read` / `search` / `fetch` / `think` 的选 `allow_once`；`execute` 和其他选 `reject_once`。
  - `cli` → 选 `reject_once`（P1 没有 UI 可以问用户；拒绝后 emit 一条现有 `deniedText` 风格的 notice，告诉用户可以把权限改成 edits/full 或切回 `-p`）。
  - 找不到对应 kind 的选项就回 `cancelled`。
- 用户停止本轮时，所有还没回复的权限请求回 `cancelled`。
- 每次自动回答都写一行 `onLog`（工具名 + 决定）。

### 3.7 `agyOutcome.ts` —— 伪装成 end_turn 的错误（设计 11.1，最重要）
- 会话库：`<隔离HOME>/.gemini/antigravity-cli/conversations/<sessionId>.db`（复用 `history.ts` 的 `withDb` 和 `agyConversationDb`；sessionId 必须匹配 `/^[\w-]+$/`，否则跳过检测）。
- prompt 发出前读 `select max(idx) from steps` 记为起点（库不存在记 -1）。
- prompt 返回后读 `idx > 起点` 的步骤，取最后一步；`step_type === 17`（ERROR_MESSAGE）就判定失败。错误文本从 `step_payload` 里取可读字符串（可以用 `history.ts` 里现有的 protobuf 读取工具，或者把 payload 当 UTF-8 后用下面的正则在里面找，截断到 16KB 再找）。
- 解析：
  - `/Error (\d{3}), Message: (.+?), Status: ([A-Z_]+|\d{3}[^,\n]*)/s`
  - `/([A-Z_]+) \(code (\d{3})\): ([^\n]+)/`
  - 有 `reason:QUOTA_EXHAUSTED`、HTTP 429、`RESOURCE_EXHAUSTED`，或匹配 `RATE_LIMIT_RE` → 限流：`emit({ t: 'rate_limited' })`，`rateLimited: true`。
  - `quotaResetTimeStamp:<ts>` / `quotaResetDelay:<go duration>` / `retryDelay:<go duration>` 能解析就写进错误信息（例如“约 3 分钟后重置”），P1 不用接到用量窗口。
  - `thinking.signature: Field required` 或 ``Invalid `signature` in `thinking` block`` → 错误信息明确告诉用户“这个会话历史已损坏，无法继续，请新开对话”（i18n）。
- 读库失败只写 `onLog`，不影响结果（退回只看 stopReason）。
- 在实现前，先用 `sqlite3` 或 node 脚本看一眼真实库（例如 `"/Users/oneday/Library/Application Support/agentswitch/profiles/gemini-efe62d/home/.gemini/antigravity-cli/conversations/"` 下的 `.db`）里 `steps` 表的结构确认字段名；**只读，不要写这些库**。

### 3.8 停止（设计 11.2）
`RunHandle.kill()`：
1. 如果 `session/prompt` 还没写进 stdin（还在等会话/模型设置），直接中止流程，结果 `stopped: true`，不发 cancel。
2. 已发出：发 `session/cancel { sessionId }` 通知；所有挂起的权限请求回 `cancelled`。
3. 等 `session/prompt` 返回（预期 `stopReason: 'cancelled'`），最多 15s；超时就 `pool.retire(profileId)`（终止进程组），结果仍是 `stopped: true`。
4. `kill()` 多次调用要幂等。

### 3.9 回退
- `pool.acquire` 或 `initialize` 失败（不含用户停止）→ `onLog` 写原因，`emit notice`（i18n：“ACP 启动失败，本轮改用普通模式”），然后**本轮直接改走现有的 `-p` adapter**（同一个 `runAgent` 调用内完成，调用方无感）。
- 同一账号连续 3 次启动失败后，本次应用运行期间这个账号固定走 `-p`（内存里记，不写配置）。
- 会话阶段（resume/new 之后）失败不回退，直接按 3.5.9 报错，避免同一条消息被发两次。

## 4. 测试（vitest）

至少覆盖：
1. `jsonrpc`：半行拼接、非 JSON 行、请求/响应配对、错误响应、超时、agent → client 请求被 handler 处理并回写、未注册方法回 -32601、`close()` 让挂起请求全部 reject。用 `PassThrough` 流做假的 stdin/stdout。
2. `stderr.sanitize`：每种令牌 / URL / HOME 路径都被替换；4KB 尾部截断。
3. 事件映射：用第 2 节实测的真实消息做 fixture（`tool_call` → `tool_call_update(pending)` → `in_progress` → `completed` → `agent_message_chunk` → `usage_update` → prompt 结果），断言产生的 `AgentEvent` 序列，特别是工具卡片 id 稳定、`kind: execute` 归为 run。
4. 权限自动回答：`full` / `edits` / `cli` 三种模式 × `execute` / `edit` / `interaction_` 请求，断言回的 optionId 或 cancelled。
5. `agyOutcome`：用 `node:sqlite` 在临时目录建一个 `steps(idx, step_type, step_payload)` 表的假库，覆盖：无新增步骤、最后一步是 15（正常）、最后一步是 17 且含 `RESOURCE_EXHAUSTED`（限流）、含 thinking signature 错误、库不存在。
6. 同会话串行：两个 prompt 并发，第二个要等第一个返回后才写进 stdin。

不要写依赖真实 agy 或网络的测试。
